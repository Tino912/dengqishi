## LightKnight MVP —— 修复试玩反馈的两个缺陷

用户反馈：①与掌灯人对话后"判定为死亡" ②返回标题黑屏。两个都已定位并修复。

### 排查方法（有效，值得复用）
不靠猜。用浏览器探针把 `Game` 的状态机逐步打出来（`tools/make-regress.py` 的前身）：
逐帧记录 `mode / menuKind / menuStack / hp / player.dead / prog.deaths / #fade 的 class`，
并在 `playerDie` / `hurtPlayer` 上装钩子记录调用栈。
同时也把可疑状态**截图**下来看——"死亡界面"和"商店返回后"长得完全不同，一眼就能分辨。

### 根因一：返回标题黑屏
`#fade` 是全屏纯黑遮罩（`z-index:30`，高于 `#overlay`）。
`handleAction('totitle')` 会 `fade(true)` 拉黑转场，但 `toTitle()` **没有配对的 `fade(false)`**
（`startLevel`/`respawn` 都有）。黑幕永远留在最上层。
→ 修：`toTitle()` 补 `fade(false)`，并复位 `pending/deathDelay/cut/menuStack`。

### 根因二：与掌灯人交互后卡死（两个 bug 叠加）
(a) **菜单返回栈压进陈旧值**。`showMenu` 里 `menuStack.push(this.menuKind)`，
但战斗中 `mode==='play'` 时 `menuKind` 还是陈旧的 `'title'`。
于是地图上按 E 开商店 → 栈里压 `'title'` → 点「返回」弹出**标题菜单**，
`mode` 卡在 `'menu'`，世界停止推进 → 玩家按键无反应，看起来像"被判死亡"。
→ 修：返回栈改成 `MenuFrame = MenuKind | 'play'`，压栈时
`this.mode === 'play' ? 'play' : this.menuKind`；`backMenu()` 遇 `'play'` 就 `closeMenu()`。

(b) **死亡结算被菜单吃掉**。原写法：
```ts
if (this.deathDelay > 0) {
  this.deathDelay -= dt;                                  // 不管什么模式都在减
  if (this.deathDelay <= 0 && this.mode === 'play') { … } // 模式不对就不弹
}
```
倒地后有 1.9s 延迟。这期间若在菜单/对白里，倒计时在看不见的地方走完，
**死亡界面永不再出现**，`player.dead` 永远为 true → 卡死只能刷新。
→ 修：倒计时限定 `mode==='play'` 内推进；同时倒地后禁止开暂停菜单。

### 顺带修掉
- **关卡三无法通关**：渡口发出 `{type:'victory'}`，但 `main.ts` 写的是 `case 'victory': break;`
  （空实现），终章触发不了。→ 改为路由到 `handleAction('victory')`。
- 从菜单/对白回战斗给 1.1~1.4s 无敌，避免"刚关面板就被贴脸打死"。
- 商店/升级面板底部操作条改 `position: sticky` 常驻。矮窗口下「返回」原本被滚出可视区。
  注意：`.menu` 有 `max-width:420px`，做全宽遮罩时要覆盖成 `max-width:none`，
  按钮给固定宽度，否则下方卡片文字会透过操作条。

### 教训
- 这类"多界面来回切"的状态机缺陷，`tsc` / 构建 / 逻辑仿真**全都测不到**，
  必须用真实浏览器驱动完整交互流程。已固化为 `npm run verify` 的 15 条回归断言。
- 写断言别硬编码累计值（`deaths` 跨用例累加），要用基线增量。

## ✅ 已做：Godot 光照最小验证（用户已装 godot 4.7.2，直接开跑）

新目录 **`godot-probe/`**（独立于 Web 版，互不影响）+ 一键脚本 **`tools/godot-probe.sh`**。
工程只做一件事：`project.godot` + `main.tscn` + `probe.gd`，场景全在代码里构建，无外部素材。

### 做法（可复用）
- 渲染走**固定 1280x720 的 `SubViewport`**，与窗口尺寸解耦 —— 这点是被逼出来的：
  先直接跑，窗口被 WM 改成 **1270x1528**，画幅不对、取样全错。
- 6 个用例，**同一场景只改一个变量**：`shadow_on_add` / `shadow_off_add`（对照）/
  `shadow_on_mix` / `energy_high` / `inset_10` / `inset_24`。
- 每例等 8 帧 → 游戏自己 `get_image()` 回读像素 → 存 PNG + 写 `report.json` +
  向 stdout 打 `LKRPT…ENDLKRPT`。断言写在 `probe.gd` 的 `_judge()` 里，脚本按退出码判定。

### 结论
- **遮挡成立**：墙后正对灯处，开阴影 **0.0482** vs 关阴影 **0.3308**，**降 85.43%**。
  远角两组都是 0.0482 不变 → 是墙挡的，不是光斑变小。
  `energy=2.6` 时墙后**仍是 0.0482** → 阴影随亮度稳定成立。
- **亮度运行时可调**：energy 1.2→2.6，均亮 0.2379→0.3805，光斑明显变大，阴影形状不动。
  正是"连击提高亮度"需要的性质。
- 混合模式差别不大：ADD 均亮 0.2379，MIX 0.2268。
- **→ 结论：Godot 的遮挡光照确实是 Web 版做不到的质变**（Web 版光会穿墙）。换引擎的理由成立。

### 意外发现：墙会遮挡自己（已量化为规则）
遮挡体轮廓与墙的视觉**完全重合**时，墙自己的表面落进自己的阴影（射线到灯要穿过自身遮挡体）。
**规律非常干净：受光深度 = 遮挡体内缩量。**

| inset | d=2 | d=6 | d=20 | d=37 |
|---|---|---|---|---|
| 0 | 0.215 边缘 | 0.024 影 | 0.024 影 | 0.032 影 |
| 10 | 0.409 亮 | 0.239 亮 | 0.024 影 | 0.032 影 |
| 24 | 0.409 亮 | 0.303 亮 | 0.232 亮 | 0.032 影 |

（未受光墙体基准 0.0315）内缩**不漏光**：inset 10/24 的墙后都还是 0.0482。
→ 这是**创作选择**不是 bug：重合 = 边缘勾亮的暗剪影；沿墙脚放 = 墙面正常受光。

## 第二探针 · 2.5D 俯视下的遮挡体摆法（已完结）

用户选 A：把迁移前最后一个未知数打掉。做法：`godot-probe/probe25d.gd`（22 用例，
4 种来自 `levels.ts` 的真实墙型 × 4 个光照方向 × 4 种遮挡体摆法 + 灯形状对照），
`tools/godot-probe25d.sh` 一键复现，结论写在 `godot-probe/README-2.5D.md`。
**注意：跑指定场景要把场景当位置参数传（`godot --path . res://probe25d.tscn`），
否则会跑 main.tscn。**

### 结论（可直接落地）
遮挡体 = **屏幕上画出来的整体轮廓**（顶面 ∪ 南立面），**只把底边削 ~16px**；
不要贴地面足迹，也不要四边均匀内缩。

### 三条与我预判相反的发现
1. 脚印模型的漏光点在**墙顶上方**（墙后地面 0.4834 vs 轮廓 0.0482，10×），不在侧面（侧面 0.0482 全黑）。
   原因：灯与足迹同高，水平光线必被挡，只有向上的光能翻过足迹上沿。
2. "墙越窄漏得越厉害"错了——**宽墙/厚块才需要轮廓模型**；窄柱两种模型都亮（0.60/0.42），
   因为光本来就绕得过去。
3. 第一探针的"四边均匀内缩"**不能搬到 2.5D**：轮廓上沿就是墙顶，内缩它等于削墙顶 →
   侧光从墙顶漏进去（墙后 0.3153 vs 0.0482）。**只削底边**才不漏。

### 其他要点
- 削底量是美术旋钮：`墙脚受光高度 ≈ 削底量 − 1~3px`；削 8px 侧光下亮不起来（0.33px），
  削 16px 才在任意方向都亮（正面 15px / 侧面 13px）；代价是墙脚光从底座溢到另一侧约 13%（0.1058）。
- **正面光下"贴足迹"与"贴轮廓"数值完全相同** —— 所以这个决策只影响侧光/背光，坑很难早期暴露。
- 背光时脚印模型会把墙面照亮（0.324 vs 剪影 0.0255）。
- 厚块的墙脚在侧光下不亮是几何必然（足迹深 248px，灯在中高处，射线必穿遮挡体下半身），不是缺陷。
- **2.5D 的灯必须竖压成椭圆**：屏幕正圆在同一地面距离上北/东 = 1.6968（纵向多照 70%），
  竖压椭圆 = 1.007。**Web 版现在用的正是屏幕正圆（`render.ts` applyLighting 的
  `createRadialGradient`），也就是"连击提高亮度"在地面上是各向异性的，南北多照 60%。**
  这条与换不换引擎无关，可以独立先修。

### 仍未覆盖
墙在屏幕上是轴对齐矩形（斜置/L 形没测）；只测 4 个离散光照方向；灯放在脚底
（若建模成抬高的灯笼，正确遮挡体会落在"足迹"与"轮廓"之间）；像素值依赖 llvmpipe。

### 一键复现结果（刚跑，rc=0）
```
断言 75/75 通过 · 全部通过 ✅
墙前 0.3284　墙后 开 0.0364 / 关 0.0953　射程外（同帧基线）0.0367
墙后降幅 61.8%　墙后/底噪 开 0.99× 关 2.60×　墙前/底噪 8.95×
灯的形状 东 0.0867 / 北 0.0871 = 1.0046
```
命令：`tools/godot-lightknight.sh`（约 10~60s，需 X11/XWayland，不能 `--headless`）。

### 核心结论（迁移到底值不值 → 值）
**Light2D + LightOccluder2D 真的能挡住光，Web 版不能。** 证明方式的关键是
「同帧基线」：`s_far` 取在灯半径外、完全照不到的点，用**同一张图里**的它当底噪，
才能排除伪因「墙后本来就照不到」。
- 开阴影：墙后 0.0364 ≈ 底噪 0.0367（0.99×）→ 已压到"照不到"的水平
- 关阴影：同一点 0.0953（2.60×）→ 光其实够得着，只是被墙挡了

对照截图 `shots/05-occlusion-on.png` / `06-occlusion-off.png`，只切换
`PointLight2D.shadow_enabled` 一个变量。

### 真实 bug：叠加层不标脏
`Bloom` 是独立 `CanvasItem`，`World.step()` 只对自己 `queue_redraw()` →
加法混合层（玩家地面光池 / 灯芯辉光 / 挥击亮芯）**冻结在最后一次重绘的瞬间**，
症状是玩家脚下光池不跟人走、半径也不变。修法：`bloom.queue_redraw()`。
**顺带把玩家脚下那圈烘焙光池从 `0.55×`/`0.30×` 收到 `0.26×`/`0.15×`** —— 它是
`_draw` 画的、不认遮挡，一大团暖光会糊在墙后阴影上，正好抵消 LightOccluder2D 的意义。

### 从 Web 版补回的行为（初版漏了）
1. Boss 贴身接触伤害（`d < e.r + p.r + 6`）—— 漏了站 Boss 身边不掉血，压迫感全无。
2. 敌人移动的恒定阻尼 `damp(v,0,2.6,dt)` + 撞墙 `v*=-0.2`。
   **这是敌人实际速度的真实来源**（约标称的 0.69×），不补敌人快 45%。Boss 撞墙眩晕 1.1s。
3. 敌人互相分离（`updateEnemies()` 互推），避免叠成一团。
4. 近战结算改为「前摇结束当帧结算 + 前冲动量（guard 240 / 其他 150）+ 挥击特效」。
5. 对白翻页补 `E`/`F` 键（原来只有 confirm）。

### Godot 4 踩坑（7 条，详见 README 第六节）
1. 从 `Array`/`Dictionary` 取值不能 `:=` 推断（`var h := w[4]` → 编译错）。
2. `just()` 边沿要求「按下—松开」，`_tap` 只置位不归位会让对白永远卡第一句。
3. **协程在第一个 `await` 就让出控制权**：漏 `await` → 后面的段落在后台**并发**跑，
   断言前提错位、截图拍到"别人已改过的世界"。铁证是两张本该不同的截图**字节相同**。
4. 对白期间世界冻结（`advance()` 在 `state=="dialogue"` 不 step）→ Boss 过场不点完，
   后面 `_pump(240)` 一步不动。
5. 见上「叠加层不标脏」。
6. 别写「离墙还有 20px」这种想当然阈值 —— 碰撞解算把玩家正好顶在墙面，稳态间隙=玩家半径。
7. 本机 `/tmp` 10MB tmpfs，Godot 的 `TMPDIR` 必须指真实磁盘（脚本已处理）。
