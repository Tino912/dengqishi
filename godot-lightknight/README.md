# 灯骑士 · Godot 版

用 Godot 4 把「灯骑士」做下来的第二个实现。它**起步**于一次迁移实验，但现在已经不
只是实验了 —— 见下面「四、与 Web 版的关系」。

最初要单独考察的那件事是：

> **用 Godot 的 `Light2D` + `LightOccluder2D`，光能不能真的被墙挡住。**

Web 版的光照是 Canvas 合成手搓的（全屏压暗 → `destination-out` 挖洞 → 叠暖光）。
那套做法**没有遮挡关系，光会穿墙**——对「地图黑暗，只有灯骑士周围些许亮」
这个核心机制来说，是质变级的差别。结论：**能挡，值得迁移**（见 二.1）。

在此之上，Godot 线继续往前走了：**8 把武器 / 19 个技能**（每把武器一套自己的技能、
不同的连击门槛与冷却）、**精英词缀**、**肉鸽三选一**、以及**第二关「无芯之暗」**
（火盆与不死再生、盲女同行、分阶段 Boss）。最近几轮又做了 **HUD 自绘重制 + 战斗特效贴图化**
（见 二.9）、三选一改成**只有 `Q`/`E` 移动、只有 `空格`/`回车` 拿走**（见 二.8）、
**宝箱 / 背包栏（多带一把武器）/ 守灯人的重铸与锤炼**（见 二.10），
**宝箱与敌人落点的每局随机生成**（见 二.12）、
**武器随机元素属性 + 攻击自己会发光 + 第三关「灯河渡口」**（见 二.13），
以及最近这一轮的 **夜色提亮 + 起步攻击范围 + 迷雾**（见 二.14）——
现在有**三张风格各异的地图**、十种造型各异的敌人，地图是"看得清地形但确实是晚上"，
没被照亮的地方盖着一层会飘的雾，**灯照到哪里，哪里的雾就散开**。

一、运行
--------------------------------------------------------------------

```bash
# 一条命令：真实引擎里跑完整自检，产出 shots/*.png + shots/report.json
tools/godot-lightknight.sh
```

预期输出结尾是 `断言 358/358 通过` / `全部通过 ✅`，退出码 0。全程约 30 秒。

手动跑 / 想自己玩：

```bash
cd godot-lightknight
godot --path . res://scenes/main.tscn --rendering-driver opengl3
```

按键：`WASD` 移动　鼠标瞄准　`J`/左键 挥击　`Shift`/`Space` 冲刺　`1`/`2`/`3` 技能　`E`/`F` 交互
　`X` 换手（手持 ↔ 背包武器）　`C` 喝灯油（背包里的回血道具）
　`Enter`/`Space` 确认对白　`R` 重开　`Esc` 暂停
　（清空一波后会弹三选一：**只有 `Q`/`E` 能左右移高亮，只有 `空格`/`回车` 能拿走**，
　`Esc` 放弃这次。见 二.8。地图上的**宝箱**开出带词条的武器、**守灯人**能重铸/锤炼武器，
　见 二.10。）

> 自检必须**带显示环境**跑（X11 或 XWayland）。它要读 `SubViewport` 的像素来判定
> 「黑不黑、亮不亮、光有没有被挡住」，`--headless` 的 dummy 渲染器读不出画面。

二、验证结果
--------------------------------------------------------------------

### 1. 遮挡照明（最初那条结论）

同一场景、同一采样点、**只切换 `PointLight2D.shadow_enabled` 这一个变量**：

| 采样点 | 开阴影 | 关阴影 |
| --- | --- | --- |
| 墙前（灯与墙之间） | 0.6152 | 0.6152 |
| **墙后** | **0.1460** | **0.2730** |
| 射程外（同帧基线 = 地板底噪） | 0.1744 | — |

```
开阴影时：墙后 0.1460，光的**增量** = 0.1460 − 0.1744 = −0.028（已压到照不到的底噪以下）
关阴影时：墙后 0.2730，光的**增量** = 0.2730 − 0.1744 = +0.099（光其实够得着，只是被墙挡了）
墙后亮度降幅 46.5%　墙前光的增量 +0.441
```

> ⚠️ **这一组从"比值"改成了"增量"**（地图提亮那一轮改的），而且**必须**改：
> 底色从 0.008 涨到 ~0.17 之后，`墙后/射程外` 的比值只剩下 0.84× / 1.57×——
> 光贡献的那 0.07 被 0.17 的底色一除，就量不出东西了。**"光有没有照到这一点"本来就是加法**，
> 除法在这里只会把底色混进来。比值仍旧记进报告，只是不再当判据。

「同帧基线」是这套实验的关键：`s_far` 取在灯半径之外、完全照不到的位置，
用**同一张图里**的它当底噪，才能排除「墙后本来就照不到、所以怎么测都暗」这个伪因。
`shots/05-occlusion-on.png` 与 `06-occlusion-off.png` 是这一组的对照截图——
开阴影那张，阴影边界从墙的东沿切线般拉开，墙后整片全黑。

### 2. 灯必须是「地面正圆」而不是「屏幕正圆」

2.5D 斜轴测下，屏幕上的正圆投到地板上是椭圆，会导致「南北方向比东西方向亮 70%」。
做法是把灯的贴图**纵向压扁 0.62**（与投影同一个 `YSQUASH`），于是它投到地面正好是正圆。
实测地面等距的东/北两点：

```
东 0.2526 / 北 0.2534 = 1.0032     （屏幕正圆会是 ~1.65）
```

### 3. 遮挡体的摆法

结论来自迁移前的两次探针（`godot-probe/`，见两份探针 README）：

- 贴**地面足迹** → 光会从墙顶翻过去照到墙后（实测墙后亮 10 倍），不行；
- 轮廓四边**均匀内缩** → 会从墙顶漏光，不行；
- **贴屏幕上画出来的整体轮廓（顶面 ∪ 南立面），只把底边削掉 16px** → 唯一正确解。

削底量直接决定「墙脚受光高度」：削 8px 在侧光下完全亮不起来，削 0 则墙脚全黑。
所以 `LightRig.OCC_TRIM = 16.0` 是个有依据的常数，自检里有三条几何断言看着它。

### 4. 八把武器 / 19 个技能：**特效**要真的分开，不是改数字

这是这一轮新增内容里最容易糊弄过去的地方 —— 把 8 把武器写成同一套挥击、只换
`dmg` 数字，断言照样能全绿。所以判据不是「伤害不同」，而是**打出来的特效种类不同**：

| 武器 | 手感定位 | 技能（连击门槛 / 冷却） |
| --- | --- | --- |
| 灯刃 `blade` | 最初的短刃，连击攒得最快 | 旋斩 4/2.2　灯爆 12/7.0 |
| 双灯刃 `twin` | 最快，单下很轻，靠连击层数顶伤害 | 乱影刃 4/2.4　双旋 11/6.0 |
| 长明枪 `spear` | 距离长、突刺强，**技能最多** | 掠光刺 3/1.8　连灯刺 9/5.0　长明贯 18/10.0 |
| 锁灯 `chain` | 近战里够得最远，能把影子**拽回来** | 链锁 5/3.0　环链 13/6.5 |
| 烬锤 `hammer` | 慢、重、范围极大，**只有一招** | 撼地 7/3.6 |
| 灯镰 `scythe` | 弧最宽，一扫小半圈；**别停** | 回旋 5/2.6　噬影 14/8.0　月环 22/11.0 |
| 灯弩 `crossbow` | **唯一远程**：挥击不再是刀弧，而是射出光矢 | 三连矢 3/2.0　穿影矢 10/5.5　灯雨 20/10.0 |
| 灯杖 `staff` | **唯一法术**：能在黑暗里「留下」东西 | 灯球 6/5.0　护光 14/9.0　陨光 24/12.0 |

自检把 8 把武器 / 19 个技能**逐个跑一遍**，每次出手后立刻采一次 `effect.kind`
（`beam`/`muzzle` 这类只活 0.06~0.2 秒，等 `_pump` 完再看就已经过期了 —— 这一条
曾经因此漏判）。实测：

```
8 把武器　19 个技能　玩家侧特效 7 种
burst, muzzle, pillar, pull, ring, slash, zone
```

外加 **Boss 独占的 `beam`**（吸灯光束 / 回旋光刃），归 Boss 那一段验。
这些特效背后是有行为的，断言也照着行为写，而不是照着"画面有东西"写：

- `pull` 链锁真的把敌人拽近：**420 → 274.8px**（`拉近 > 40px` 才算过）
- `zone` 灯球真的按 tick 反复结算，不是只打一下：1.3 秒内总伤害 **122.6**，命中集 ≥ 1
- `bow_pierce` 一根光矢真的穿过 ≥ 2 只排队站着的敌人
- `staff_ward` 护盾期间被咬**不掉血**
- `scythe_devour` 噬影窗口内造成伤害真的**回血**

`shots/11-weapon-staff-orb.png` 是灯杖的一张实拍：HUD 上是「武器 灯杖」，
左下角三个技能各自标着连击门槛（灯球 6 / 护光 14 / 陨光 24），
画面中央是一颗留在原地、持续灼烧的灯球 —— 与初始的灯刃完全不是一种东西。

### 5. 第二关「无芯之暗」+ 肉鸽循环

设计稿里有一句：「在其中一关，没灯芯，黑暗中怪和 Boss 不断再生」。第二关就是这一关。

| | 第一关「灯堡外庭」 | 第二关「无芯之暗」 |
| --- | --- | --- |
| 地图 | — | **2800×2000**（更大） |
| 环境亮度 `ambient` | 0.9 | **0.955**（更黑） |
| 敌人倍率 | 1.0 | **1.18** |
| 墙体 | — | 16 面 |
| 机制 | — | **火盆 3 座**、未点满则死亡再生、盲女同行 |
| Boss | 噬灯者·幼体 | **噬灯者**（devourer，带护佑减伤） |

- **再生**：火盆没点满时，死掉的影子会**复活**（自检里实测再生 5 次）；
  点满 3 座火盆后再生停止、Boss 的护佑（减伤 55%）同时解除。
- **盲女**：古老灯芯所化，跟着你走，**靠近时光照半径恰好多 52**
  （实测 `150 → 202`，差 0.0 误差）—— 就是设计稿里那句
  「可你在我身边时，我就感到格外亮堂」。她不会被攻击、不挡路，是「灯」不是「队友」。
- **分阶段 Boss**：噬灯者的招式池**随血量阶段变化**。这点很关键 ——
  满血时是 phase 1，池子只有 `dash/dash/slam/summon`，**再打也放不出光束**；
  掉到 1/3 才进 phase 3，池子里才有 `drain`（吸光）和 `sweep`（横扫）。
  自检因此先把它打到 phase 3 再验 `beam` 出没出。

**肉鸽循环**：清空一波 → 弹**三选一**（3 个选项，可能是恩赐，也可能是换武器）。
整个自检跑下来共发生 **7 次**三选一。选它是真的改东西：

- 选「武器」→ `prog["weapon"]` 与场上 `player.weapon_id` 同时换掉
- 选「恩赐」→ 恩赐入账，且**数值真的作用到派生属性上**：
  「灯芯·锋」提高伤害、「灯芯·明」提高光照半径、「灯芯·疾」降低挥击冷却、
  「省火」降低技能消耗（但有下限 1，不会白嫖）

**14 个恩赐**（灯芯·坚/锋/疾/明/远/通/锐、噬影、火种不熄、越战越亮、影步、省火、
灯油丰沛、灯灭之环）。**5 个精英词缀**，让同一个精英每局不一样：
燃（死亡爆火圈）、韧（减伤 35%）、疾（更快更勤）、噬（额外咬掉连击）、障（每 4 秒挡一次伤害）。

波次编排也做了种子随机（`_roll_waves`）：每局敌人组合与数量不同，但**完全可复现**。
**波次与 Boss 的落点、以及宝箱的位置，也是每局重摇的**（见 二.12）——
关卡表 `content.gd` 里那份坐标现在只是"数量"和"撒不出来时的兜底值"。

### 6. 机器人试玩 90 秒（不预设数值，只看循环通不通）

```
击杀 74　最高连击 13.0　最低生命 -3.0　清空波次 3/3　三选一 7 次　阵亡 3　打到 Boss ✅
```

（阵亡 3 次是**设计内**的：机器人在菜单里按下 `R` 爬起来接着打，计数器只是记录。
布局随机化之后波次散到全图、路程变长、接触变多，所以击杀从 32 涨到 74。
真正的那一票是右边三项：**清空波次 3/3 · 三选一发生 · 打到 Boss**。）

机器人用真实输入（`GameInput.set_override()`，走 `just()` 边沿）驱动世界，不读内部
状态作弊。它同时是**肉鸽循环的端到端证明**：它会自己清波、自己点三选一、
一路打到 Boss 区。这一段曾经抓到两个隐蔽的 bug：

- 清空一波后世界被三选一面板**冻结**，机器人不会选 → 卡死在那，症状是
  「击杀数停在第一波、Boss 永不出现」。看起来像战斗坏了，其实是界面没点。
- 死亡后停在死亡菜单里空转，后面几十秒**静默**浪费，同样表现为「击杀数不动」。

### 7. 三层验证

| 层 | 命令 | 验的是什么 |
| --- | --- | --- |
| 编译 | `godot --headless --path . --import` | GDScript 静态类型/语法全过 |
| 仿真 | 自检里的逻辑段 | 波次、Boss 三阶段、连击衰减、技能门槛等纯逻辑 |
| **真引擎** | `tools/godot-lightknight.sh` | 324 条断言，含**像素级**的遮挡对照与灯形状判定 |
| **变异** | `tools/godot-mutate.py` | 故意改坏实现，确认**只有**对应断言变红（证明断言不是摆设） |

自检是**确定性**的：关卡内的随机数全部走 `level["seed"]` 播种（第一关 10711、第二关 20422、
第三关 30733），布局随机化另走 `Main.run_seed`（自检把它钉成 `selfcheck.gd` 里的
`LAYOUT_SEED = 20260925`），武器元素则走 `_elem_rng`（见 二.13）——
连跑两遍 `report.json` **逐字节相同**（当前基线 md5 `fa02dae73042b6983de1cab170691a19`）。
这条曾经被破坏过，原因是
`EnemyState.create()` 里用了**全局未播种的 `randf()`** 来决定敌人的绕行相位 ——
而那个相位是**进仿真**的（`sin(e.t * 1.6 + e.wob)` 直接加进 `vx/vy`），
所以每趟跑出来的世界都不一样。症状极隐蔽：断言照样全绿，只有机器人试玩那段数值每次不同。
修法见 六.8。

### 8. 三选一的输入规则：只有 Q/E 移动，只有空格/回车拿走

原来的三选一是 `1`/`2`/`3` **直接选中**、`←`/`→` 移光标。问题是**误触的代价太大**：
清空一波往往正打着手，`1`/`2`/`3` 又紧挨着技能键，手指一滑就把这一局的选择赔进去了。

现在改成**两段式**：

| 动作 | 键 | 其余一律无效 |
| --- | --- | --- |
| 左移高亮 | `Q` | `A` 不行（`A` 是移动） |
| 右移高亮 | `E` | `D` 不行 |
| 拿走高亮那张 | `空格` / `回车` | `J` / 鼠标左键（攻击）不行 |
| 放弃这次 | `Esc` | —— |

再加一条 **0.35 秒装填窗口**（`Main.DRAFT_ARM`）：面板刚弹出的 0.35 秒内按确认**不生效**，
底部会显示一条装填进度。理由是"清波那一瞬间玩家手上常常正按着空格在冲刺"，
这个边沿会被面板吃到 —— 换成"必须停一下再确认"，误触就消失了。

这一段在自检里是**逐条可失败的断言**，不是"看起来该是那样"：

```
面板刚弹出时还没装填完 ✅
装填窗口内按确认无效（防误触：清波瞬间常在连打空格冲刺）✅
1/2/3 在三选一里已彻底失效（不再直接选中）✅
A/D 不会移动三选一高亮 ✅
J 不能确认三选一（攻击键在这里无效）✅
E 把高亮右移一格 ✅ ／ Q 把高亮左移一格（回到原位）✅
Q 从第一格再左移会绕到最后一格 ✅ ／ 绕回来仍是原位（左右对称）✅
确认拿走的就是高亮那一张（不是第一张）✅
```

其中"**每一条都要能真的失败**"这点很关键：`1`/`2`/`3`、`A`/`D`、`J` 这三组
如果代码里还留着老分支，对应的断言立刻变红；把断言删掉就检测不到了（这坑踩过，见 六.13）。

### 9. UI 与特效这一轮的翻新

用户要的是"整体 UI 和特效更好看一些"。这一轮做了三件事，**都不动玩法逻辑**：

1. **HUD 全部改成自绘控件**。原来 HUD 用 `StyleBoxFlat` 堆，做不到渐变条、辉光、
   扇形冷却这三样。现在血条/灯条/Boss 条是 `RBar`（渐变 + 滞后残影 + 冷却刻度 + 告急闪烁），
   技能格是 `SkillChip`（热键牌 + 连击菱形 + 冷却线），三选一是 `DraftCard`
   （渐变卡面 + 徽记 + 受选上浮与金描边），另有 `ArmBar` 装填条与 `PanelLamp` 角灯。
   卡片按 `_boon_sig` 签名缓存，只在内容变了才重建。
2. **光晕改成真渐变贴图**。原来 `Art.glow()` 是**几十个同心圆**叠出来的，凑近看是一圈圈
   同心环。现在换成运行时生成的 256×256 `soft_dot`（smootherstep 衰减），
   并且**预先降采样**（运行时贴图没有 mipmap，不降采样会有采样噪点）。
3. **战斗特效接上真素材**。挥击弧、命中火花、弹道拖尾、火盆/灯塔火焰、
   击杀余烬与烟，全部换成 Kenney 粒子包里的贴图（`Art.tex()` / `tex_rot()`），
   位置与旋转照旧由代码算 —— 随机项一律走种子的 `_rng`，所以**确定性不变**。

| `assets/fonts/LXGWWenKai-Regular.ttf` | 标题、连击数等展示字体 | [霞鹜文楷 LXGW WenKai](https://github.com/lxgw/LxgwWenKai) | OFL-1.1 |

> **素材是"运行时加载"的**，故意绕开 Godot 的导入管线：
> `Image.load_from_file(ProjectSettings.globalize_path(...))` → `ImageTexture.create_from_image`。
> 这样 `--import` 之外的一键自检**不需要** `.import` 文件，也不会因为缺 `.godot/imported`
> 而在裸仓库里读不到图。代价是没有 mipmap / 压缩（所以就手动降采样到 256）。

### 10. 宝箱 / 背包 / 守灯人（重铸与锤炼）

这一轮加的是"**局内多一把武器 + 给武器加词条**"这条线。四件事：

| 东西 | 在哪 | 说明 |
| --- | --- | --- |
| 宝箱 | 每关 2 个 | 按 `E` 开，从**3 把**里挑一把，选中进**背包**；开过的箱子不会复活 |
| 背包栏 | 右下角 | 手持武器 + 它的词条 + 备用武器 + 灯油存量 |
| `X` 换手 | 任意时刻 | 手持 ↔ 背包 互换；**背包空时什么都不做**（不做"把自己缴械"） |
| `C` 喝灯油 | 任意时刻 | 消耗一件回 45% 生命；**没药 / 满血都不消耗**（不让人白扔一瓶） |
| 守灯人 | 每关 1 个 | 按 `E` 交谈，开商店：买灯油（22 灯火）、重铸（45）、锤炼（30 + 15×等级和） |

**重铸 vs 锤炼**（这次最容易做含糊的一处，所以说死）：

- **重铸** = 把词条**全部推倒重来**：随机 1~3 条、等级归 1、彼此不重复。
- **锤炼** = 没满 3 条就**加一条**；满了就**升一级**；全练到 5 级后**不再受理，也不收钱**。

词条一共 8 条，全部落在**已有的派生属性访问器**上（不在别处再乘一遍）：

| 词条 | 效果 | 落点 |
| --- | --- | --- |
| 锋 | 伤害 +12% | `damage_mul()` |
| 疾 | 挥击冷却 −10% | `attack_cd_mul()` |
| 远 | 攻击范围 +12% | `reach_mul()` |
| 锐 | 暴击率 +8% | `crit_chance()` |
| 噬 | 击杀回复 3 点生命 | `_kill_enemy()` |
| 明 | 光照半径 +22 | `player_light_radius()` |
| 火 | 每次命中额外 +0.15 连击 | `combo_bonus()` |
| 省 | 技能连击消耗 −1（最低 1） | `skill_cost()` |

**词条挂在「武器 id」上，不是挂在"当前手持"上**（`prog["waffix"] = {武器id: [{id,lv}]}`）。
所以换手不丢、换回来还在，背包里那把也各自带自己的词条；实测断言里专门验了这一条。

两条设计决定，都是为了**别把已经量好的世界搅动**：

1. **宝箱不写进 `level["props"]`，而是单独一个 `chests` key**，并且在 `_decorate()`
   **之后**才入 `props`。因为 `props` 里每一项都要 `_decor_rng.randi_range` 抽一个 seed，
   而 `_decorate()` 又会躲开已有道具 120px —— 提前加进去，整关装饰都会换位置，
   依赖装饰的像素断言会**成片**变红。实测：加宝箱前后 `report.json` 里除新段落外的数字**逐字节未变**。
2. **宝箱故意不 solid**。它是个"交互点"不是障碍；设成实心会插进 `collide_wall` 的推挤里，
   而动线与撞墙那几条断言是拿现有道具布局量出来的，多一个实心体就可能把玩家顶到别处。

**随机源分了五条**（`_rng` 主仿真 / `_decor_rng` 装饰 / `_shop_rng` 商店 /
`_chest_rng` 宝箱 / `_layout_rng` 布局）。**除了 `_rng`，其余都绝不能走主仿真流** ——
主仿真流里每一步被消耗多少由"玩家第几步走到哪儿"决定，往里面插随机数会把之后
所有世界演化整体挪掉（"步数就是货币"）。布局随机化见 二.12。

#### 这段的断言是怎么写"死"的

一共 61 条（当时 232 总数里），要点是**每一条都能真的失败**。写完之后做了一轮**变异测试**：
故意改坏 6 处实现，确认**只有**对应的断言变红、没有连带误伤：

| 故意改坏 | 变红的断言 |
| --- | --- |
| `swap_weapon()` 改成空操作 | 按 X 与背包武器互换 · 换手后玩家手上真的换了武器 |
| `damage_mul()` 里删掉「锋」 | 词条「锋」真的进了伤害倍率 |
| `_can_temper()` 去掉等级上限 | 词条全部到上限后锤炼不可点了 |
| `use_potion()` 里 `healed` 置 0 | 按 C 喝灯油会回血 · 回血量正好是 45% 最大生命 |
| `apply_chest()` 不写 `bag_weapon` | 宝箱选中的就是高亮那一张 · 背包已满时换下旧的 · 手持没词条那把时「锋」回到 0 |
| 移动高亮时不带面板文案 | 宝箱面板按方向键后标题与提示不会被重置成三选一 |

最后一条是自己刚踩的坑：`_draft_input()` 每次按 `Q`/`E` 都会重调 `show_draft()`，
不把文案一起带上，**宝箱面板一按方向键就会退回三选一的标题**。
现在标题/副标题/底部提示存在 main 上（`_panel_title` 等），三选一与宝箱共用重画路径。

**三个会让世界冻结的界面**（这是本项目最容易把自己搞死的地方）：
`dialogue`（对白）、`draft`（三选一，**开宝箱也走这个状态**）、`shop`（守灯人商店）。
`_pump(n, hold, auto_draft, auto_dialogue, auto_shop)` 默认**三个都自己处理掉**；
少点一个，后面所有段落会成片变红（敌人不动、镜头不跟、灯不亮），极难反查。

几个刻意的设计选择：

- **数据 / 逻辑 / 绘制三层分开**。`content.gd` 是纯数据，`world.gd` 是纯状态推进，
  `art.gd` 只负责画。所以自检能直接读世界状态做断言，不需要去解析画面。
- **程序化为主、贴图只做"点缀"**。几何（地形、角色、灯）依旧全用 `draw_*` 画出来，
  外部贴图只用在"渐变/粒子"这类手画不好看的地方。好处仍是工程可整包复制、
  素材都带许可；代价是贴图**运行时加载**（见 二.9 的注）。
  CJK 字体优先用仓库里的霞鹜文楷，取不到时回退系统 `/usr/share/fonts/noto-cjk/`。
- **固定步长，游戏与自检走同一条代码路径**。`Main.advance(1/60)` 既被 `_process`
  的累加器按真实帧驱动，也被自检直接调用 N 次（自检把 `Main.manual` 打开，
  `_process` 直接 return，所以 `await` 渲染帧期间世界**不会**偷偷推进）。
  自检才有意义：它跑的就是玩家会跑的那条路径。
- **输入自己做边沿检测**，不用 `Input.is_action_just_pressed()`：世界是按固定步长
  推进的，自检更是脚本直接驱动，基于帧的 `just_pressed` 语义在这种驱动方式下不可靠。
  另外提供 `set_override()`，让自检完全不依赖操作系统的输入栈。

四、与 Web 版的关系
--------------------------------------------------------------------

**核心机制差异（迁移的收益）**

| | Web 版 | Godot 版 |
| --- | --- | --- |
| 光被墙挡 | ❌ 光穿墙 | ✅ `LightOccluder2D` 真遮挡（墙后/底噪 0.99×） |
| 灯的形状 | 屏幕正圆（地面被拉成椭圆） | 地面正圆（贴图纵向压 0.62） |
| 墙脚受光 | 无此概念 | 削底 16px，墙脚有受光带 |

**⚠️ 内容上 Godot 线已经跑到前面了**

原先的约定是「跨版本改玩法时，以 Web `src/game/*.ts` 为准，Godot 版照抄」。
从这一轮起这条**不再成立**，下面这些在 Web 版里**没有对应实现**，Godot 版是唯一实现：

- 8 把武器 / 19 个技能（Web 版是 3 把武器）
- 14 个恩赐 + 三选一肉鸽循环
- 5 个精英词缀、种子随机的波次编排
- **宝箱 / 背包栏（多带一把武器）/ 守灯人的重铸与锤炼 + 8 条武器词条**
- **每局随机生成的宝箱与敌人/Boss 落点**（`run_seed` 一次开局一个种子）
- 第二关「无芯之暗」：火盆与不死再生、盲女同行、分阶段 Boss
- **8 把武器各随机一种元素**（火/冰/雷/毒/光）+ 对应状态（灼烧/冻结/麻痹连锁/中毒减速/对暗影加伤）
- **攻击自己会发光**：挥击的刀锋灯与每颗弹丸的灯，都走真遮挡（会被墙挡）
- **第三关「灯河渡口」**（Web 的三关是另一套数值与关卡，没有元素也没有攻击发光）
- **三张地图各一套美术风格**（court / quarry / river，不是换色）+ 敌人身子登记表
- 敌人 `扑灯蛾 moth`、`灰烬鬼 ashling`、`灯河浮尸 tidehusk`、`衔灯兽 lanternjaw`

所以：**下次要动这些内容，得先决定以哪边为准**，别默认"Web 是权威"。
反过来，Web 版仍是一到三关数值调平的参考 —— 那边有商店/升级/存档，Godot 版还没有。

**刻意保留的差异（有理由）**

1. **玩家脚下的烘焙光池半径从 `0.55×` / `0.30×` 收成 `0.26×` / `0.15×`**。
   Web 版把这圈当成「唯一的光」所以开得很大；但它是 `_draw` 画的、**不认遮挡**，
   一大团暖光会直接糊在墙后的阴影上，正好抵消 `LightOccluder2D` 的意义。
   现在只留贴着脚的一小圈暖芯，真正的照明交给会被墙挡住的那盏 `PointLight2D`。

**移植过程中补齐的、Web 版本来就有而初版漏掉的行为**

2. **Boss 的贴身接触伤害**（Web `world.ts` 的 `d < e.r + p.r + 6` 那条）。
   漏了它的症状很直观：站在 Boss 身边完全不掉血，Boss 失去压迫感。
3. **敌人移动的恒定阻尼与撞墙反弹**。Web 版 `moveEntity()` 每帧对速度做
   `damp(v, 0, 2.6, dt)`，外加撞墙 `v *= -0.2`——这一条是**敌人实际速度的真实来源**，
   阻尼后约为标称速度的 0.69 倍。不补的话敌人在 Godot 版里会快 45%。
   还有一条：Boss 冲撞撞墙要眩晕 1.1s。
4. **敌人互相分离**（Web `updateEnemies()` 里的互推），避免叠成一团。
5. **敌人近战攻击的结算方式**：改为「前摇结束当帧结算 + 前冲冲量（guard 240 / 其他 150）
   + 挥击特效」，与 Web 版一致。
6. **对白翻页键**补上 `E`/`F`（Web 版用 `Space`/`E`/`F`/`Enter`）。

### 11. 修回三条会"静默失败"的 bug（全屏闪光残留 ×2 + 三选一徽记错位）

这三条来自一次外部 PR（`maxlen727` 的 `fix/godot-fx-residual`，提交 `55cb837`）。
那个 PR 曾被合并，后来因为要先保住本地工作被强推退掉了，所以**这三条是我们自己重新实现的**
（不是 cherry-pick；基线已经被宝箱/背包/守灯人那轮改过，直接套用会错位）。
`git fetch origin refs/pull/1/head` 随时能把原提交取回来对照。

三条的共同点是**都不会报错、也不会让断言变红，只是画面上悄悄不对**：

| # | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 换关卡 / 重生后，上一关死亡的**红闪一直盖在新画面上** | `flash_rect` 挂在**常驻 HUD** 上，而 `flash_power` 是 **World 实例**成员。`hud.refresh()` 只在 `power > 0` 时写颜色，新世界从 0 开始，那个分支**永远不再走** | `refresh()` 补 `else: flash_rect.color = Color(0,0,0,0)` |
| 2 | 死亡红闪**卡在结算画面上**不动 | 闪光衰减原本写在 `world.step()` 里，而对白 / 菜单 / 三选一 / 商店期间世界被冻结（`advance()` 不调 `step()`） | 抽成 `World.tick_fx(dt)`，由 `main.advance()` **无条件**调用 |
| 3 | **多张恩赐卡长得一模一样**（徽记回退默认图） | `Hud.EMBLEMS` 的键还是老版本恩赐 id（`bright`/`fuel`/`kindle`/`greed`/`heavy`/`dr`/…），与 `content.gd` 现在的 id 完全对不上 | 按 `content.gd` 的 `WEAPONS`/`BOONS`/`WEAPON_AFFIXES` 重写 |

`tick_fx` **不消耗任何 RNG**，所以"世界冻结期间也推进表现层"不会挪动随机流 ——
确定性自检（连跑两遍逐字节相同）不受影响。

#### 一个意外的收获：原来的遮挡断言是**擦着阈值过**的

修完 bug 2 之后，遮挡那一段的数字全变了。原因不是光被改坏，而是**原来的采样被污染了**：

`set_post_enabled(false)` 只关**暗角**层，**管不到 `flash_rect`**（它就是一块全屏 `ColorRect`）。
而遮挡那一段正好会连续弹几段对白把世界冻住 —— 旧的衰减写在 `step()` 里、对白期间不跑，
于是**一发残留的闪光一直糊在采样区上**，给每个采样点加了个近似常数，把"墙后 vs 底噪"的比值压平：

| 断言 | 修复前 | 修复后 |
| --- | --- | --- |
| 墙前 / 射程外 ≥ 3× | 16.3× | **48.5×** |
| ★ 关阴影时墙后 > 射程外 ×2 | **2.04×**（险过） | **5.25×** |
| ★ 开阴影时墙后 ≈ 底噪（≤ 1.15×） | **0.99×**（几乎必然通过） | **0.61×** |
| 墙后降幅 | 75.8% | **94.2%** |

也就是说，这两条"核心结论"断言原来是在**逼近一个被污染的比值**上勉强成立的。
顺手记一条规则：**任何全屏叠加层只要不在 `set_post_enabled` 的管辖内，就必须在采样前
显式确认它是透明的** —— 否则像素断言测的是叠加层，不是光。

#### 这段的断言（8 条，每一条都能单独失败）

徽记 3 条（在 `_section_assets`）：
1. `EMBLEMS` 覆盖**全部**武器 / 恩赐 / 词条 id（不靠 `star_06` 兜底）
2. `EMBLEMS` 的每个值都能被 `Art.tex()` 解析成**真实贴图**（写错一个字母不会报错，徽记会直接隐形——比回退更糟）
3. 卡片可见 id 的贴图**有区分度**（同一张最多被 2 个 id 复用），防"十张卡一个样"退化

闪光 5 条（在 `_section_drops_death`）：
4. 死亡瞬间红闪**确实亮在屏幕上**（给后面几条制造真实前提，否则"清掉了"是同义反复）
5. 死亡期间（世界冻结）闪光照常**淡出**，且 `flash_rect.color.a` 归零
6. 结算期间**世界时间没有前进**（证明世界真的停住了——少了这条，第 5 条在"衰减其实写在 `step()` 里"的实现下也能过）
7. 重生**前**手动再点亮一次红闪并确认它在屏幕上（否则第 8 条又是同义反复）
8. 重生后全屏滤镜**已清除**（真正在盯 `refresh()` 的 `else` 分支）

第 6、7 条是刻意的"防同义反复"设计：**先断言前提成立，再断言结论**。

#### 用工具证明这些断言有牙齿

新增 `tools/godot-mutate.py`：故意改坏实现，确认**只有**对应断言变红。

最早 8 个：

| --- | --- |

### 12. 宝箱与敌人位置的每局随机生成

用户提的：**宝箱位置与敌人位置不要每关固定，要随机生成**。看起来是"把写死的坐标换成
`randf_range`"，但在这个工程里它真正的难点是**不能把确定性自检砸掉**，而且
**随机布局的失败方式全都不报错**：

| 失败方式 | 表面现象 | 靠什么抓到 |
| --- | --- | --- |
| 锚点撒进墙里 | 敌人卡在墙缝里出不来、宝箱摸不到 | `blocked()` 断言 |
| 锚点被墙隔开、走不过去 | 那波永远清不掉，**关卡卡死**，全程不报错 | `has_los` 链式可达断言 + 机器人试玩 |
| 随机没配上种子 | 连跑两遍 `report.json` 不一样 | 同种子逐点相同 / 换种子整套变 |
| 生成失败没兜底 | 少一个宝箱、少一波怪 → 撞掉一大片跟数量有关的断言 | `fallbacks == 0` 断言 |

做法：`World` 新增 `run_seed` 与独立随机源 `_layout_rng`，
种子 = `hash([run_seed, level_index, "layout"])`。`Main.run_seed` 在**开局时**由时间生成
（`new_run()`，标题界面的"开始"走这里）；**死亡重开不换种子**（同一局的挫折要给同一个地图）。
`start_level()` 把它传进 `World.setup()`，没设过就兜底生成一个。

- **宝箱**：`_roll_chest_spots()` 撒点，约束「不撞墙（留 26）· 离出生点 > 240 ·
  离灯塔 > 200 · 避让已有 `props`（96 + r）· 两箱之间 > 320」，撒不出来兜底关卡表那份。
- **敌人锚点**：`_roll_anchors()` 给 Boss 场地与每一波各撒一个点。Boss 场地留 120 净空、
  离出生点 480 / 离灯塔 260；每波留 74 净空、离出生点 360、离 Boss 380。
  锚点之间**同时卡上下限**：与"参照点"（第一波看出生点，之后看上一波）距离要落在
  **460~900**——太近会让清一波顺手清掉下一波（波次失去节奏），太远会把链条拉断
  （实测机器人直接跑到时间用尽，只清得掉两波）。

**可达性约束是这段最值钱的一条**。撒点最阴的翻车不是"撒进墙里"（那个 `blocked()` 能查到），
而是**看着在空地上、其实被一道墙跟玩家隔开**：那一波永远清不掉、关卡直接卡死，
而且**不抛任何异常、不留任何日志**，只有真的走一遍才暴露 —— 所以自检里
「机器人清完了三波」这条端到端断言，是这一层唯一的独立证人。

#### 两个"别搅动已量好的世界"的约束

1. **自检默认把"波次 → Boss"这条链停掉**（`Main.waves_off` → `World.waves_disabled`，
   在 `_update_waves()` 开头早退，**运行时每步读**，中途可开关）。
   原因：锚点现在随机，若某一波恰好落进自检早期某段的活动范围，那一波会**意外刷出**、
   又被顺手清掉、于是 `_update_waves` 判"清空"→ 弹三选一 → `state = "draft"` → 世界冻结。
   症状极隐蔽：几百行之后看似完全无关的断言失败（本轮实测：弩矢攻击被面板吃掉，
   `_tap("attack")` 后 `state` 竟是 `draft`）。只有 `_section_waves_boss()`（以及第二关那段
   验三选一的部分）会临时放开，并且**先 `restart_level()` 重建一个干净世界**。
2. **早期段落里临时移除宝箱**，用完还原。宝箱是"缝光"来源，开着会让遮挡那段的
   像素采样偏高（`set_post_enabled(false)` 只管暗角，管不到一个新加的高亮物件）。

#### 这段的断言（9 条，每一条都能单独失败）

```
宝箱点位不是关卡表里写死的那个（真的重摇过）         ← 防"随机化被静默绕过"
波次锚点不是关卡表里写死的那个（真的重摇过）
Boss 场地也不是写死那个坐标
★ 换一个局种子 → 宝箱与敌人的位置整套换了           ← 防"随机源没接上 run_seed"
★ 同一个局种子重建世界 → 点位逐点相同               ← 防"随机化砸了确定性自检的地基"
生成的宝箱点都不在墙里
生成的波次锚点都不在墙里（中心留得下落脚地）
波次锚点都离出生点够远（不会一出生就开打）
★ 波次锚点从出生点起链式可达（走不通就会卡关，而且不报错）
随机布局没有退化到兜底坐标
```

后三条是这轮"补回来"的：最初只写了"位置变了、不在墙里"，跑起来全绿，
但机器人在随机布局下**只清掉两波**——于是补了距离上下限与链式可达约束。
这也顺手说明一件事：**新断言全绿不代表新功能对**，`report.json` 里那条
「机器人清完了三波」才是端到端的那一票。

#### 变异结果（4 个，全部符合预期）

```
宝箱退回关卡表里写死的坐标      → 只红「宝箱点位不是写死那个」            ✅ 干净
敌人锚点退回写死坐标            → 红「波次锚点不是写死那个」「Boss 场地也不是」
                                  + 附加：链式可达、机器人两条            ✅ 有真实耦合
布局随机源不再吃 run_seed       → 红「换种子位置整套换了」
                                  （「同种子逐点相同」**没红** = 确定性没被砸）✅
波次锚点不校验直线通路          → 红「链式可达」+ 机器人打不到 Boss 区      ✅
```

**一个有价值的副产品**：把锚点换回关卡表那份手写坐标时，「链式可达」也变红了。
核实了一下，这不是误伤 —— 手写布局里**第 1 波 `(830,830)` 与第 3 波 `(1980,700)`
相对上一锚点都没有直线通路**（连出生点 → Boss 场地也没有）：

| | 出生点 → 第1波 | 第1波 → 第2波 | 第2波 → 第3波 |
| --- | --- | --- | --- |
| 手写布局 | ❌ 742px | ✅ 734px | ❌ 644px |
| 随机布局 | ✅ 684px | ✅ 829px | ✅ 463px |

也就是说：**手写那份布局是按"绕过去"设计的**（玩家会自己找路），而随机撒点没法保证
"一定有条一眼看得出来的路"，所以给它上了更严的约束——必须直着走得到。
这也解释了为什么随机化之后机器人的击杀从 32 涨到 74：它原先在墙前是**卡着走**的。

⚠️ 顺带留一个诚实的边界：`has_los` 在断言里是**和被约束的实现共用**的同一个函数。
如果哪天 `has_los` 自己写坏了（比如永远返回 `true`），两边会一起被骗过去。
所以这层真正的独立证人是端到端的那条「机器人清完了三波」——它走的是碰撞、移动、
敌人 AI 的真实路径，不认 `has_los`。

### 13. 武器元素 · 攻击发光 · 第三关与三张地图

用户这一轮提了四件事：**① 近战挥击与远程弹药会发光**、**② 武器带随机元素属性**
（冰能冻住、火能烧）、**③ 做出第三张地图**、**④ 三张地图风格各异、敌人样貌也各异**。

四件事在实现上是**互不相干**的，但撞在同一处：**它们都会往已经量好的世界里加东西**。
所以这一段的重点不是"功能写完了"，而是**每一条都能被断言抓住**（本轮 232 → 324 条，
新增 92 条）。

#### 13.1 元素：每局摇一次，挂在**武器 id** 上

五种元素（`content.gd` 的 `ELEMENTS`）。关键是**五种形状不同**，不是同一种 DoT 换个颜色：

| 元素 | 效果 | 设计意图 |
| --- | --- | --- |
| 火 | 灼烧 3.0s，每秒跳一次，总伤约 22% | **短促密集**——打完就走，伤害立刻兑现 |
| 毒 | 中毒 6.0s，跳得稀疏（总伤约 10%），**并减速到 0.62** | **绵长稀疏**——拉开距离的软控制，和火正好互补 |
| 冰 | 冻结 1.15s，**完全不能动**（连外力给的速度都被清掉） | 硬控，代价是短 |
| 雷 | 麻痹 0.42s 定身 + 电弧**连锁一跳**（半径 260，40% 伤害），**隔墙不连** | 清小怪的引信，不是清场 |
| 光 | 对**暗影系**敌人 ×1.30，命中**额外 +0.35 连击**；对非暗影系没有加成 | **对策**，不是"通用变强" |

> 「火 vs 毒」和「冰 vs 雷」这两对是刻意做成两种不同形状的：前者是"两个节奏的 DoT"，
> 后者是"两种失控"——冰是**完全不动**，雷是**定身 + 外溢到别人身上**。
> 如果火/毒/冰/雷都写成"掉血 N 点持续 M 秒"，这一轮就白做了，只是四个倍率。

**随机的做法**（这条比看起来讲究）：

- 用**独立的随机源** `_elem_rng = RandomNumberGenerator`，种子 `hash([run_seed, "elem"])`，
  **不带 `level_index`**。→ 元素属于**这一局**，不属于这一张图；
  **过关换地图不会重摇**，有专门断言看着它。
- 结果存 `prog["welem"] = {武器id: 元素id}`，**挂在武器 id 上**，
  和武器词条（二.10）同一套做法 → **换手 / 换回来还是同一个元素**，有断言。
- **允许重复**。8 把武器摇 5 种元素，实测 **48/48 个种子都有重复**。
  这是故意的：强制 8 把各不同，第二局就能把元素表背下来了。
- 基础攻击被染成元素色（`element_color_of()`），**弹丸的颜色是发射那一刻的快照**
  （之后换武器不会追着变），两条都有断言。

实测数据（`report.json → cases.elements`）：

```
这一局的八把：blade=fire  chain=venom  crossbow=venom  hammer=fire
              scythe=venom  spear=shock  staff=frost  twin=fire
48 个种子的分布（48 × 8 = 384 次）：fire 67　frost 83　shock 79　venom 81　radiant 74
```

分布断言写的是"**每种至少出现 20 次 / 共 384 次**"，不是"每种正好 76.8 次"——
后者在有限样本上本来就会失败。同时有一条**换种子整套换掉**（随机真的生效）
与一条**同种子逐项相同**（确定性没被随机化破坏）。

#### 13.2 攻击自己会发光（并且是**真的光**）

灯骑士的照明一直是 `LightRig` 那套（`PointLight2D` + `LightOccluder2D`，会被墙挡）。
这一轮把攻击接进去：**挥击的刀锋上一盏、每颗飞行中的弹丸一盏**。

| | 挥击 | 弹丸 |
| --- | --- | --- |
| 缓存 key | `"swing"`（恒定一盏） | `"proj:<pid>"`（跟着弹丸的稳定 id） |
| 位置 | 沿刀锋扫过：`reach` 随出招时相从满程收到 0.30、`sweep` 跟着 `facing` 扫 | 弹丸自己的坐标 |
| 颜色 | 武器的元素色 | 发射那一刻的元素色快照 |
| 半径 | **跟着武器的攻击距离走**（长兵器的光伸得更远） | 固定 60 |
| 遮挡 | `shadow_enabled = true` | 同左 |

像素实测（同一采样点，只切换"攻击中 / 收手后"这一个变量）：

```
挥击的刀锋灯   0.0783 -> 0.2070　（2.6×）
飞行中的弹丸灯 0.0921 -> 0.9348　（10.1×）
```

**必须封顶**：`FX_LIGHT_MAX = 6`。弹丸雨一次能造十几颗弹丸，一盏灯一个 `PointLight2D`
（还是开阴影的），不封顶会把帧率直接拖垮。断言是"塞 24 颗弹丸时**实际只点 6 盏**"，
外加"弹丸消失后灯被回收 / 全部结束之后归零"——**灯不回收是这种缓存最常见的坏法**
（画面看着没事，只是越来越慢）。

#### 13.3 第三关「灯河渡口」与三张**风格各异**的地图

| | 第一关 | 第二关 | 第三关 |
| --- | --- | --- | --- |
| 名字 | 灯堡外庭 | 灯堡深处 · 无芯之暗 | **灯河渡口** |
| 尺寸 | 2400×1700 | 2800×2000 | **3000×2200** |
| 美术风格 | `court` | `quarry` | **`river`** |
| ambient（越大越亮） | 0.90 | 0.955 | **0.975** |
| 敌人倍率 | 1.0 | 1.18 | **1.35** |
| Boss | 噬灯者幼体 | 噬灯者（成体） | **灯魔之影**（`shadow: true`） |
| 专属 | — | 火盆再生成 / 盲女同行 | 灯河浮台 / 浮灯 |

"风格各异"这一条**没有靠嘴说**：断言里逐关加载、各拍一张图，比较**各自出生点周围**的画面，
差异必须 > 25%；同时有一条**对照**——**同一关重建两次差异 0.00%**（证明这个比法本身是有效的，
不是"随便两张图都不同"）：

```
1 vs 2 = 41.8%　1 vs 3 = 35.2%　2 vs 3 = 30.9%　（对照：同一关重建两次 = 0.00%）
```

再加一条不依赖像素的：**三关的调色板 5 项里至少 4 项互异**。
两张一起看，才排得掉"其实只是改了 ambient 和换色"。

推进链也一起改了：`L1 → L2 → L3 → 通关`，**第三关之后不再往前**（一条专门防越界的断言）。

#### 13.4 敌人样貌各异

10 种敌人 → **9 套身子**，分派集中在 `Art.body_kind()` 的一张登记表里。
少的那个是**故意的**：噬灯者幼体与成体共用一套，另有「灯影」是兜底造型。

这条的断言写法值得抄：**不是**断言"每种敌人画出来不一样"（那种断言永远绿），而是

> **除了「灯影」本身，没有任何敌人落回兜底造型。**

新敌人（灰烬鬼 / 灯河浮尸 / 衔灯兽）忘登记 → 静默变成"又一只灯影"，
这条断言就是专门为这个失败方式准备的（变异测试里验过，见 13.5）。

#### 13.5 这一段怎么证明断言有牙齿（12 个变异）

| 故意改坏 | 变红的断言 |
| --- | --- |
| 元素不再随机（八把全摇成同一种） | ★ 允许两把武器撞同一个元素 · ★ 换种子整套换掉 |
| 元素随机源带上关卡号 + 每次建世界都重摇 | ★ 过关换地图不会重摇元素 |
| 火不再结算灼烧 | ★ 火：灼烧一直在掉血 |
| 冰不再冻结 | ★ 冰：冻结期间一步都不动 · ★ 解冻立刻恢复 |
| 雷连锁不查视线 | ★ 雷：电弧**不能穿墙** |
| 挥击灯不带遮挡 | ★ 这盏灯**带遮挡** |
| 挥击灯半径不再跟攻击距离挂钩 | ★ 灯的半径跟着攻击距离走 · ★ 挥击真的把画面照亮了 |
| 弹丸灯能量为 0 | ★ 弹丸的灯真的照亮了那一块 |
| 攻击类灯不封顶 | ★ 攻击类灯有上限 |
| 第三关之后还能继续往前 | ★ 第三关之后不再往前 |
| 新敌人漏登记造型 | ★ 除了「灯影」本身，没有敌人落回兜底造型 |
| 第三关地板退回第二关那种 | ★ 三图画面差异 > 25% ×3 |

（用法同前：`tools/godot-mutate.py 火不再结算灼烧`。）

#### 13.6 这段踩的两个坑

1. **"给敌人加一个位移"会被元素吃掉**。链锁牵引原本是给敌人一个速度冲量
   （`e.vx += cos(...) * pw`），结果：抽到**冰**的武器命中 → 冻结把速度清零 → 拽近 **0.0**；
   抽到**毒** → 减速 ×0.62 → 拽近 61 而不是 170。症状是"同一条断言因随机元素时好时坏"。
   → 改成**一次位置位移**（`yank` 112px × 重量系数）+ 清速度，与元素、减速、顿帧全部解耦，
   实测恒定 89.6px。**新加的位移效果不要经过速度**，这条值得记住。
2. **"两张图不一样"不能用整屏比**。第一次写三图差异时是整屏逐像素比，
   得到 3.5% / 3.0% / 2.6% —— 差点判成"三张图其实差不多"。真相是
   **游戏屏幕大部分本来就是黑的**，三张图的黑是同一片黑。
   → 改成按**各自玩家屏幕位置**裁剪一块再比（差异升到 25%~42%），
   并补一条"同关重建两次 = 0%"的对照。**比"黑底画面"的差异，一定要先把无关的黑裁掉。**

### 14. 夜色提亮 · 起步攻击范围 · 迷雾

这一轮的需求是三句话：**「适当提升角色初始的攻击范围」+「适当提升地图亮度，使地图可见但
类似于晚上」+「给地图添加迷雾，灯照的地方迷雾会散去」**。三件事互相独立，分开验。

#### 14.1 起步攻击范围 ×1.20

`World.reach_mul()` 的基数从 1.0 提到 `BASE_REACH := 1.20`（刀锋 66 → 79.2 世界单位）。
实现上刻意用**加法**（`BASE_REACH + 恩赐×0.12 + 词条×0.12`）而不是"整体乘一个系数"——
词条「远」每级 +0.12 是**已有的、逐级验过的**断言，乘系数会把它变成 +0.12×系数。

**为什么单独拿它出来说**：这一段里原来**一条绝对断言都没有**。所有跟范围有关的断言
都是"比基准多多少"（`reach_mul() == rc0 + 0.12`），所以 `BASE_REACH` 整体退回 1.0，
那一片断言**照样全绿**，"够不着"的老手感会静默回来。补了两条钉子：

```gdscript
_ok("★ 起步攻击范围 = 基础射程 ×1.20", is_equal_approx(rc0, 1.20))            # 钉倍率
_ok("★ 起步的刀锋真的够到 79.2", is_equal_approx(w.swing_reach(), 79.2))     # 钉落到武器上
```

变异测试 `起步攻击范围退回 1.0` 证明这两条真的会红（而词条那几条不受影响）。

顺带修掉一个**真实的回归**：机器人试玩的交手距离原本写死成 62/64/44px，那是照近战写的。
攻击范围一提升，同一个机器人会因为"永远贴到 60px 才出手"而**不会用远程武器**，
症状是"同一份代码，机器人时而清完三波、时而只清一波"。现在它按
`w.swing_reach()` 推出的距离出手（`press_in = rch*0.78`、`atk_at = rch*0.95`），
攻击范围怎么调它都跟得上。实测：击杀 83、清空 3/3 波、打到 Boss。

#### 14.2 夜色：地图可见，但确实是晚上

原来 `LightRig` 的夜色映射写错了区间：`ambient` 是 0.90 / 0.955 / 0.975，
而 `1.0 - ambient` 只有 0.10 / 0.045 / 0.025，**三关全都落在 `t = 0`** ——
于是"这张旋钮"拧到哪都是最暗那一档，地图纯黑，看不出来。现在按真实落点定标：

```gdscript
const NIGHT_MIN  := Color(0.42, 0.46, 0.60)   # 最暗那档的底色（偏冷的蓝）
const NIGHT_SPAN := 0.115                     # 真实落点区间
const NIGHT_BASE := 0.018
var t := clampf((d - NIGHT_BASE) / NIGHT_SPAN, 0.0, 1.0)
cm.color = NIGHT_MIN.lerp(Color(1.0, 1.0, 1.0), t)
```

同时三关的调色板整体提亮一档（**色相一个都没动**，只抬明度）：
第一关地板 `#1b2030` → `#2c3450`。实测全屏平均亮度：

| | 关雾 | 开雾 |
| --- | --- | --- |
| 第一关出生点 | 0.1580 | 0.2121 |
| 三关各自 | 0.16 / 0.14 / 0.12（一关更比一关黑） | — |

断言是**两头卡**的：`> 0.05`（不是纯黑）且 `< 0.45`（没亮成白天）。
`shots/21-fog-off.png` 是关雾的样子：地砖的缝、墙的顶面与南立面、脚下的暖光池都看得清，
但整体是冷的、暗的——"看得清地形"和"这是晚上"同时成立。

#### 14.3 迷雾：自己算的，不是 Light2D

**为什么不能用 `Light2D` 来"擦"雾**：2D 光照只能把**被照到**的地方画出来
（`blend_mode = ADD`），而雾要的正好相反 —— **没被照到**的地方才该有雾。
`Light2D.BLEND_MODE_SUB` 减的是 RGB，**不减 alpha**，所以"用一盏负光在雾上挖个洞"
在 2D 里做不到。结论：这张雾必须自己算。（与 `Bloom` 那层只能加不能减是同一个限制。）

做法（`src/fog.gd`）：

1. 屏幕切成 **80×45** 的格子（16px 一格），每格问一句"这里被照亮了多少"；
2. 照亮值 = `max over 灯(径向衰减 × 视线有没有被墙挡住)`，写进一张 80×45 的贴图；
3. 一个全屏着色器读这张贴图：照亮值低的地方画雾、高的地方留空，再叠三层倍频噪声当雾絮。

视线用**射线扇**而不是逐格沿线采样：每盏灯按 **192 条射线**做一次"射线 vs 墙矩形"求交
（`Proj.ray_rect_dist`，slab 法），得到**每个角度上光最远到哪儿**；
于是格子只要比一下距离就够了。代价是 `射线数 × 近处墙数`（几百次求交/盏），
比"每格 × 步数"便宜两个数量级 —— 而墙总共才十几面。

三个刻意的设计决定：

- **走固定步长**（由 `World.step()` 调），不用 `_process`；着色器里的雾絮时间也取自
  世界的 `time` —— 所以连"雾在飘"都是可复现的。（每 0.05 秒重建一次照亮场，20Hz 够用。）
- **有开关**（`set_fog_enabled`）。与 HUD 那层暗角是同一个道理：像素类断言要能把它关掉，
  否则"墙后到底暗不暗"量到的是雾。世界层亮度测量与"攻击灯加了多亮"两段都显式关掉它。
- **只认"能开雾的灯"**：玩家灯 / 灯塔 / 火盆 / 攻击类灯 / 敌人自光，各自有一个
  `KIND_SCALE`（玩家 0.82 = 让雾在光亮的**边缘**留一圈，看得见"雾退到哪儿为止"）；
  太小的灯不开雾（否则雾面上全是针孔），盏数封顶 10。

实测（`shots/20-fog-on.png` vs `21-fog-off.png` 是同一帧的两版）：

```
灯下揭示度 0.996（1 = 雾全散）      满雾格 3528/3600
同一像素：没照到的地方 0.1526 -> 0.2058（有雾）    灯下 0.5640 -> 0.5618（几乎不动）
墙挡散雾（两点到灯**同距** 240px）：空地 0.555  墙后 0.000  墙前 0.968
雾回填：灯还照着 0.555 → 不再照到 0.475 → 0.5 秒后 0.000
挥击散雾：正南 250px 0.000 → 0.434
```

「墙挡散雾」那三条是这一段最值钱的：迷雾用的是**自己那套**射线扇求交，
与 `PointLight2D` 的影子系统是两套代码 —— 所以它是"光会被墙挡住"这个核心结论的
**第二个独立证人**。而且对照做得很干净：两个采样点到灯的距离**完全相同**（差 < 0.5px），
一个在墙的直线上、一个在空旷方向，唯一的变量就是那面墙。

「雾回填」是那条尾巴：`target` 是"这一刻该多亮"（瞬间归零），`reveal` 是"画面上现在多亮"
（按每秒 1.6 慢慢掉）。于是灯扫过去会留下一道**正在合拢**的痕迹，而不是"啪"地糊回来。

#### 14.4 这段的断言（28 条，每一条都能单独失败）

`_section_fog_night()` 里 28 条，要点如下（★ 为关键几条）：

迷雾层存在且默认开着 / 它挂在世界层里（盖得住世界）/ **HUD 在自己的 CanvasLayer 上、不受雾影响** /
**脚下没有雾** / **整屏不是均匀的雾（既有照亮格也有满雾格）** / **没照到的地方雾让画面亮起来** /
**灯下几乎看不出有雾** / **夜色两头卡** / **同一帧只拧 `ambient`、全屏必须明显变暗** /
同距离的空地散了而墙后没散 / 距离相同（对照前提）/
灯刚不照了画面还亮着 → 0.5 秒后合拢 / 攻击灯也散雾 / 三关雾色互异且取自关卡表 /

（这一段的"对照前提"断言是故意留着的：**没有对照的判据立不住** —— 比如"墙后没散"只有在
"同距离的空地确实散了"同时成立时才有意义，所以要单独断言两点的距离差 < 0.5px。）

#### 14.6 五个坑（其中一个是真 bug）

1. **迷雾层的坐标系与灯光层**不是**同一个**（真 bug）。`LightRig` / `Bloom` 把
   `position` 设成 `Proj.cam_offset(cam)`，因为它们的局部空间是"世界坐标投影过来的"
   （子节点直接写世界坐标，只是 y 预乘了 `YSQUASH`）。迷雾**照抄了这句**，
   但它的局部空间其实是**屏幕空间**（`_draw()` 画整屏矩形、着色器读 `SCREEN_UV`、
   照亮场按屏幕格子铺）—— 于是整块矩形被搬到屏幕外，**只有约 53% 的屏幕被雾盖住**，
   而且盖住的那部分还是照亮场的**错位切片**（"灯下雾散"看起来对不上灯的位置）。
   这个 bug 不会报错、不会抛异常，只是画面"有点怪"。发现它的方式是
   **把 fog_on 与 fog_off 两张截图相减、打一张 ASCII 亮度图**：
   增量只在屏幕上半部分有值，一条水平硬边横在第 400 行 —— 那不是设计，是矩形画歪了。
2. **屏幕空间的滞后状态不能跨相机移动来比**。验"雾会回填"时第一版把玩家
   `teleport` 走（以为"灯离开了"），结果 `reveal` 直接读到 0，看起来像"雾瞬间合拢"。
   真相是：照亮场是**屏幕空间**的，相机一移动，同一个世界点就落到别的格子上去了，
   量到的是"另一格的历史"。→ 改成**不搬相机**：让连击掉光、光照半径自己缩回去，
   那个点就出了灯范围。顺带一提，这条也说明**屏幕空间的滞后在滚动时依然成立**：
   人往前走，世界往后退，滞后自然变成"拖在身后的一道雾"。
3. **"整体提亮"会让逐像素差异断言退化成恒真**。三张地图"风格各异"原来比的是
   "有多少像素长得不一样"（阈值 25%）。提亮之后底色从 0.008 涨到 0.17，
   **任何两张图都有 ~99% 的像素差 > eps** —— 那条断言变成恒真，
   全绿也不再说明任何事。→ 加了一个 `_diff_ratio_norm`：**先各自减掉自己那块的平均色**
   再比，把"整体明暗 / 统一色偏"这个自由度消掉，剩下的差异只可能来自结构与纹理。
   实测三张图 88.1% / 93.2% / 97.6%，而"同一关重建两次"在两种度量下都是 **0.00%** ——
   对照还在，判据才立得住。
   （写这个度量时自己踩了一下：第一趟统计有效样本、第二趟忘了跳过越界占位符，
   于是"有效差异数"超过了"有效对数"，吐出 101.6% 这种不可能的值。**这类指标要能自证**。）
4. **雾的浓淡是拿眼睛调的**。第一版 `MIST_MAX = 0.58`，测出来"雾让画面变亮了 0.053"
   一切正常 —— 但人眼看过去，没被照亮的地方被压成了**一整块灰板**，
   地砖的缝、墙的轮廓全糊掉，而用户要的是"地图**可见**"。
   降到 **0.40**，并把**倍频噪声从两层加到三层**（原来噪声格又大又少，看着就是一块灰板）。
   **数字全绿 ≠ 观感对**：这类"整体观感"的东西必须把两版截图并排看。
5. **一条"没牙"的断言是靠变异测试才暴露的**（本轮唯一一次变异不符合预期）。
   "夜色"最初只有两条断言：`mean > 0.05` / `mean < 0.45`。变异 `夜色永远压到最暗一档`
   （把 `t` 写死成 0）**跑出来 0 条变红**。查下来不是补丁打歪了，是**命题本身错了**：
   地图提亮之后，即便 `CanvasModulate` 一直取 `NIGHT_MIN`，画面也只是**暗掉一半**，
   全屏均值照样落在 0.05~0.45 里 —— "不是纯黑"这个命题对"夜色卡在最暗"这个失败方式
   **天然不敏感**（它防的是**提亮之前**那个底色 0.008 的年代）。
   → 补一条**只拧一个变量**的对照：同一帧、同一世界，把 `world.ambient` 拧到最暗，
   全屏均值必须明显下降（实测 0.2121 → 0.1732，差 0.039 > 0.02）。
   这条才是"夜色旋钮真的接在画面上"的对应判据，也是这轮唯一新加的断言（357 → 358）。
   **教训**：断言没红时，先分清是"补丁没打在生效的那一层"还是"断言根本问错了问题"；
   后者要靠**让旋钮转一下**（单变量前后对照）来修，不是把阈值调松。

### Godot 4 相关

1. **GDScript 从 `Array`/`Dictionary` 取值不能直接用 `:=` 推断**。
   `var h := w[4]` 是 Variant，编译器会直接报
   `Cannot infer the type of "h" variable`。要么 `float(w[4])`，要么显式声明类型。
   从 `Array` 里 `for` 出来的循环变量同理（`for side in [-1.0,1.0]` 里的 `side`
   也不能 `:=` 出 `float`）。
2. **`just()` 语义要求「按下—松开」**。自检的 `_tap()` 一开始只置位、不归位，
   于是连续两次 `_tap` 之间不会形成第二次边沿，对白永远卡在第一句。
   → `_tap` 必须"按下走一步、松开再走一步"。
3. **GDScript 协程在第一个 `await` 处就让出控制权**。`_run()` 里漏掉
   `await _check_boot()`，后面的段落就和它**并发**推进了——断言前提错位、
   截图拍成"别人已经改过的世界"。发现它的铁证是两张本该完全不同的截图
   **字节完全相同**。
4. **对白期间世界是冻结的**（`advance()` 在 `state == "dialogue"` 时不调 `world.step()`，
   与 Web 版行为一致）。所以 Boss 出场那段过场对白不点完，后面 `_pump(240)`
   一步都不会推进——"Boss 会攻击玩家"必然测不到。
5. **叠加层必须显式标脏**。`Bloom` 是独立的 `CanvasItem`，`World.step()` 里只对自己
   `queue_redraw()`，于是那层加法混合（玩家地面光池、灯芯辉光、挥击亮芯）
   **冻结在最后一次重绘的瞬间**。症状：玩家脚下的光池不跟着人走、半径也不变。
6. **断言别写「离墙还有 20px」这种想当然的阈值**。碰撞解算会把玩家正好顶在墙面上，
   稳态间隙就等于玩家半径；正确判据是「圆心 + 半径不超过墙面」。
7. 本机 `/tmp` 是 10MB 的 tmpfs，Godot 的 `TMPDIR` 必须指到真实磁盘，
   否则进程会莫名其妙崩。一键脚本里已经处理。

### 自检怎么写才不会骗自己（这一轮新踩的，代价都不小）

8. **参与仿真的随机数必须来自种子，不能用全局 `randf()`**。
   `EnemyState.create()` 里 `wob = randf() * TAU`，`wob` 是敌人绕行的相位，
   而它直接进 `vx/vy` —— 于是每趟跑出来的世界都不同，
   「连跑两遍逐字节相同」这条就废了。改成按 id 铺开黄金角
   （`fmod(float(eid) * 2.39996323, TAU)`）：彼此不同、分布均匀、完全可复现。
   **排查线索**：只有依赖玩家行为的那几段（机器人试玩）对不上，纯逻辑断言全绿。
9. **会冻结世界的界面不止一种，`_pump` 必须把两种都点掉**。
   `dialogue` 和肉鸽的 `draft` 都不调 `world.step()`。少点一种，
   后面所有段落会**成片**变红，症状是一大堆看似无关的断言同时失败
   （敌人不动、镜头不跟、盲女不跟人走、灯不亮…）。
   `_pump(n, hold, auto_draft, auto_dialogue)` 默认两种都自己处理；
   专门要验它们的那几段（"面板真的弹出来了""过场对白点得完"）把对应的 `auto_*` 关掉。
10. **"对比前 vs 对比后"必须把其他变量全冻住**。
    「盲女在身边更亮」这条最初测出 `248 -> 248`（差 0）。原因不是逻辑错，
    而是**基准值本身就含了那 +52** —— 玩家已经在盲女身边站了 8 秒。
    而且光照半径里还有 `combo`、`glow`（挥击辉光）两个会变的项，
    其中 `glow` 一旦被写成 1.0 就**不再衰减**（只有 Boss 倒下时才被写成 1.0）。
    → 正确做法：把 combo/glow 归零、保证无敌、只改盲女的位置，
    相邻两步各测一次。现在断言是"差**恰好** 52"（允许 0.5 误差），比"大于"强得多。
11. **多走一步都会挪动 RNG 流**。为了加一张截图而多推 6 步，
    结果撞掉了几十条断言之后的「链锁把敌人拽近」。固定步长 + 全局单流 RNG 下，
    步数就是"货币"。要么别多走，要么**补回来**
    （`_pump(6)` + 截图 + `_pump(74)`，总数仍是原来的 80）。
12. **分阶段的东西要按阶段验**。Boss 的 `beam` 分阶段才有：
    phase 1 的招式池里根本没有 `drain/sweep`，满血 Boss 打死也放不出光束。
    第一次写这条断言时它一直失败，查了半天才发现不是特效坏了，是**阶段没到**。
13. **"收集到的东西"要有断言消费它，否则是死代码**。
    这一段从 `_collect_kinds` 采集特效种类的逻辑写好之后，断言那行在改动中丢了，
    变成"采集了但没人看" —— 表面上 129/129 全绿，实际上"特效真的不同"这条**根本没在验**。
    补回来后立刻抓到 `beam` 的真实归属问题（见 12）。
14. **新加的随机点位会"跨段落污染"，症状出现在几百行之外**。
    波次锚点随机之后，某一波可能正好落进自检早期某段的活动范围：那一波**意外刷出**、
    被那段顺手清掉、于是 `_update_waves` 判"清空" → **弹三选一 → 世界冻结** →
    之后所有 `_tap` 都被面板吃掉。实测症状是"弩矢攻击没射出"这种看起来完全无关的失败
    （`_tap("attack")` 之后 `state` 竟是 `draft`）。
    → 修法是给世界一个沙盒开关（`waves_disabled`），自检默认把"波次 → Boss"这条链停掉，
    只在专用段落放开、并**先 `restart_level()` 重建干净世界**。
    → **排查这类问题时判据要客观**：用 `git worktree add ~/.cache/dqbase <上一轮提交>`
    把上一轮代码检出到独立目录跑一遍，证明"上一轮在同样数值下是绿的"，
    才能确认这不是本次改动引入的（本轮就是这么排除掉"弩段是我改坏的"这个误判的）。
15. **"撒得合法"不等于"走得通"**。`blocked(x, y, r)` 只能查"这一点在墙里"，
    查不出**"这一点与玩家之间隔着一道墙"**。后者不报错、不抛异常、日志干净，
    只是那一波永远清不掉 → 关卡静默卡死。要沿直线按步长采样判通路（`has_los`）；
    而且因为波次是**链式**的（清完这波才去下波），要按"上一波 → 这一波"链式判，
    不是每一波都对着出生点判 —— 对着出生点判会过严，实测会把撒点逼到兜底。
16. **"给敌人一个位移"不要经过速度**。链锁的牵引原本是速度冲量
    （`e.vx += cos(pa) * pw`），加元素之后它变得**时好时坏**：抽到冰（冻结清速度）拽近 0.0，
    抽到毒（减速 ×0.62）拽近 61 而不是 170。同一条断言因"这一局武器摇到什么元素"而红绿。
    → 改成一次位置位移 + 清速度，与元素/减速/顿帧全部解耦。**新加的位移效果别走速度通道**（见 二.13.6）。
17. **比"黑底画面"的差异必须先把黑裁掉**。三张地图"风格各异"最初用整屏逐像素比，
    得到 3.5% / 3.0% / 2.6% —— 三张图的黑是同一片黑，把真正的差异淹掉了。
    → 改成按**各自玩家屏幕位置**裁剪一块再比（25%~42%），并补"同关重建两次 = 0%"作对照。
    这类断言还要**同时**有一条不依赖像素的（这里是"调色板 5 项 ≥4 项互异"），
    否则"比法本身失效"时看不出来（见 二.13.3）。
